#### 2. 回环裁剪算法

高德 API 返回的轨迹偶尔会出现"绕圈"问题——在校园内部路禁行的情况下，高德会绕到校外主干道再回来，产生多余的环路。我们实现了两层裁剪：

- **向北折返检测**：正常公交轨迹一路向南（纬度单调递减），遇到纬度明显向北增大（>20米）的冗余点直接剔除
- **环路检测**：如果当前点非常接近之前某个已保留的点（约50米内重复），说明绕了一圈回来，去掉中间环路

```python
def _trim_loops(coords):
    trimmed = [coords[0]]
    for i in range(1, len(coords)):
        prev = trimmed[-1]
        cur = coords[i]
        # 向北折返 → 剔除
        if cur[0] > prev[0] + 0.0002:
            continue
        # 环路检测 → 绕回来就去掉中间段
        loop_back = -1
        for j in range(len(trimmed) - 2, max(-1, len(trimmed) - 30), -1):
            if (abs(cur[0] - trimmed[j][0]) < 0.0005
                    and abs(cur[1] - trimmed[j][1]) < 0.0005):
                loop_back = j
                break
        if loop_back >= 0:
            trimmed = trimmed[:loop_back + 1]
            continue
        trimmed.append(cur)
    return trimmed
```

## 踩坑与复盘

### 坑1：高德 API 轨迹不贴合预期

**问题**：最初不加任何途经点时，高德把一号食堂到二号食堂的轨迹绕到了西边，经过行知楼，不是我们想要的沿东缘主干道的弧线。

**解决**：在东缘那条实际南北路上加一个途经点 `(110.3045, 25.0622)`，引导高德沿东缘道路向南，而不是向西折回。

### 坑2：轨迹出现多余环路

**问题**：高德 API 在某些路段会绕一个圈（比如二号食堂到南大门之间，先向西沿中心环线走一段，再回头向东），视觉上多了一圈。

**解决**：实现 `_trim_loops` 环路检测算法，识别"绕一圈回到之前经过的点"的模式，自动裁掉中间冗余段。

### 坑3：改代码后页面没变化

**问题**：修改 Python 文件后只刷新浏览器页面，地图轨迹纹丝不动。

**解决**：Streamlit 需要重启进程才会重新加载代码。Ctrl+C 终止后重新 `streamlit run app.py`。

## 总结

这次实验完整走了一遍数据看板从需求到落地的流程：

- **需求分析**：从实验要求出发，确定了天气概览 + 校园地图 + 数据分析三大模块

整体来看，Vibe Coding 的核心不是让 AI 直接生成完美代码，而是**需求拆解 + 过程管控 + 结果验证**——你得知道自己要什么效果，然后不断调试、验证、修正。

### 问题 2：数据"假"在一眼就能看出来

最直接的质疑是一句反问：**"人流最多肯定是教学楼吧？"**——当时榜首却是食堂。翻数据集，问题一串：

- 一行 `1230 人次 / 79%`，容量算不出来，使用率与人是两条独立的随机数
- 所有数值都是 10 的整数倍
- 一天只有一个总数，没有时段分布

**重做方案**（`tools/generate_flow_dataset.py`，约 350 行）：

1. **先定容量，再反算使用率**：`使用率(%) = 人流量 / 容量 × 100`

| 建筑 | 容量（日累计人次） | 依据 |
| --- | --- | --- |
| 行知楼 | 3,500 | 主教学楼，同时容纳人数 × 上下课批次 |
| 教四楼 | 2,800 | 同上 |
| 图书馆 | 2,500 | 座位 × 每日进出频次 |
| 三号食堂 / 一号食堂 / 二号食堂 | 2,000 / 1,850 / 1,250 | 座位 × 每日翻台 2~3 次 |
| 一号组团 / 二号组团宿舍 / 研究生公寓 | 1,500 / 1,400 / 800 | 住宿人数 × 每日进出人次 |
| 南大门 / 东1门 / 博文后门 | 1,500 / 900 / 600 | 日均通行人次 |
| 菜鸟驿站 / 校医院 | 900 / 450 | 日均服务人次 |
| 田径场 / 新体育馆 | 1,000 / 900 | 傍晚集中活动 |
| 终点站 | 1,400 | 公交站日均客流 |

2. **让教学楼成为峰值**。教学楼一天多个上下课批次，累计人次最高；食堂只在饭点集中，一天翻台 2~3 轮。最终排行与反算：

```text
行知楼   2,792 人次  79.8%   ← 2792 / 3500
图书馆   2,271 人次  90.8%   ← 2271 / 2500
教四楼   2,257 人次  80.6%   ← 2257 / 2800
一号食堂 1,238 人次  66.9%   ← 1238 / 1850
三号食堂 1,234 人次  61.7%   ← 1234 / 2000
```

3. **数值不再整齐**：类型活跃度区间（教学楼 0.52~0.80、图书馆 0.60~0.86、食堂 0.44~0.70）+ ±5% 噪声；次日课更满，整体系数 ×1.08。
4. **固定种子可复现**：种子取 `md5(建筑名|日期)`，重跑永远得到同一份数据。
5. **注入 13 条脏数据**：文本空格、完全重复、缺失（日期/名称/人流）、`使用率=NA`、越界（-50 / 99999 / 120）、斜杠日期、清单外点位各若干条，总计 47 行。

清洗报告（第二版真实输出）：

```text
原始数据 47 行 → 清洗后 34 行
剔除关键字段缺失行：3 条
数值越界：人流量 2 条、使用率 1 条 → 置空后按同类型中位数填补
中位数填补空值：4 个
剔除建筑清单外的点位：2 条
按 (日期, 建筑名称) 去重：删除 8 条
```

### 问题 3：只有日总量，看不出"什么时候人多"

新增 `data/campus_flow_hourly.csv`（48 行 = 2 天 × 24 小时），按早 8:00 / 午 12:30 / 晚 18:00 三个高斯峰分配，并把舍入差额补到峰值小时，保证**各小时合计 = 当日总人流**：

```text
2026-11-17: 日汇总 14749 / 分时合计 14749  ✅
2026-11-18: 日汇总 16525 / 分时合计 16525  ✅
```

对应图表 `render_hourly_line()`：两条线同轴对比，11-17 蓝、11-18 红，三个峰的位置与强弱一眼可见。

### 问题 4：天气区被核心指标"压住"了

**第一轮**：天气当时被缩成一行小字（"13℃ / 61% / 28km/h / 阴"），整页最抢眼的是四个大数字指标卡。改回 4 张 `st.metric` 放到标题正下方。

**第二轮**：又被指出"四个框大小不一"。根因是 `st.metric` 高度随内容自适应：

- "总人流量"多一行 `↑ +12.0% 较前一日`
- "人流峰值建筑"的 value 是文字"行知楼"，还带一行 `↑2,792 人次`
- 另外两张只有一行值 → 被前两张撑高，视觉上参差不齐

最终用 CSS 统一，靠 `st.container(key=...)` 生成的 `st-key-*` 类名精准分组：

```python
# 所有指标卡等高 + 内容垂直居中
div[data-testid="stMetric"] {
    min-height: 136px; display: flex;
    flex-direction: column; justify-content: center; }

# 天气卡：绿色渐变 + 绿边框 + 大字号，做成整页最醒目的一块
.st-key-weather_cards div[data-testid="stMetric"] {
    min-height: 152px; border-left: 5px solid #2e7d32;
    background: linear-gradient(135deg, #ffffff 0%, #e3f2e6 100%); }
.st-key-weather_cards div[data-testid="stMetricValue"] > div {
    font-size: 2.35rem !important; }

# 核心指标：字号收敛，降低视觉重量
.st-key-kpi_cards div[data-testid="stMetricValue"] > div {
    font-size: 1.5rem !important; }
```

```python
with st.container(key="weather_cards"):
    w1, w2, w3, w4 = st.columns(4)
    ...
with st.container(key="kpi_cards"):
    c1, c2, c3, c4 = st.columns(4)
    ...
```

这样天气 4 卡既更高（152px）、又更大（2.35rem）、还带绿色渐变，而核心指标收敛到 1.5rem——主次一眼分得清，同一组内四卡严格等高。

### 问题 5：定时刷新把整页卡住

最初用 `time.sleep(60) + st.rerun()` 实现定时刷新，结果是整个页面每 60 秒重建，地图和图表跟着重绘，交互被打断。

改成局部刷新：

```python
@st.fragment(run_every=60)
def _render_weather_block_auto():
    _render_weather_block()
```

只重跑天气区块，地图、图表、筛选状态全部保留。

### 这轮最值钱的一句话

数据不是"编得像"就行，得**能当场验算**：随手点开一行 `行知楼 2,792 / 79.8%`，`2792 ÷ 3500 = 79.8%`，对得上；`16,525` 是 17 栋楼当天人流的加总，也对得上；分时曲线的 24 个小时加起来，还是 16,525。老师抽查任何一个数字，三秒内能验完——这才是"数据准确性"该有的样子。
